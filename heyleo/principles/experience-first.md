# Principle: experience first

**When**: a product, UX, or scope tradeoff comes up.

**Rule**: choose what the user experiences over what is convenient to build. Fewer polished features beat more rough ones.

## Do
- Describe the change from the user's side first: what they see, click, and wait for.
- Cover the states users hit: empty, loading, error, and long content.
- Cut scope rather than ship a rough version of everything.

## Don't
- Expose an internal limitation to the user because it is easier ("refresh the page to see it").
- Leave error messages that only make sense to a developer.

## Check
- Would the user notice this tradeoff? If yes, is it worth it for them?
